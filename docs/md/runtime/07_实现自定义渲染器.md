# 07_实现自定义渲染器

### 一、为什么要抽离renderer

如果把`document.createElement`、`appendChild`、`setAttribute`全部直接写进`runtime-core`，那么这套运行时只能服务浏览器DOM。

但Vue的核心思想是：

```text
runtime-core
  负责组件、vnode、patch、更新

runtime-dom
  负责浏览器DOM操作

其它平台
  提供自己的host操作
```

所以，`runtime-core`不直接依赖浏览器，而是通过`createRenderer`接收一组平台操作函数。

### 二、createRenderer接收host函数

当前`createRenderer`的入口是：

```ts
export function createRenderer(options) {
  const {
    createElement: hostCreateElement,
    patchProp: hostPatchProp,
    insert: hostInsert,
    remove: hostRemove,
    setElementText: hostSetElementText
  } = options;

  // render、patch、mountElement等核心逻辑

  return {
    createApp: createAppAPI(render)
  };
}
```

这里通过解构给平台函数加上`host`前缀，是为了和运行时内部的业务函数区分开。例如：

- `hostCreateElement`：平台负责如何创建节点；
- `hostPatchProp`：平台负责如何设置属性；
- `hostInsert`：平台负责如何插入节点；
- `hostRemove`：平台负责如何删除节点；
- `hostSetElementText`：平台负责如何设置文本。

而“什么时候创建、什么时候更新、什么时候删除”，仍然由`runtime-core`决定。

### 三、runtime-dom如何接入浏览器

`runtime-dom`提供浏览器平台的具体实现：

```ts
function createElement(type) {
  return document.createElement(type);
}

function insert(child, parent, anchor) {
  parent.insertBefore(child, anchor ?? null);
}

function remove(child) {
  const parent = child.parentNode;
  if (parent) {
    parent.removeChild(child);
  }
}

function setElementText(el, text) {
  el.textContent = text;
}
```

然后创建一个浏览器renderer：

```ts
const renderer = createRenderer({
  createElement,
  patchProp,
  insert,
  remove,
  setElementText
});
```

对外导出的`createApp`只是这个renderer上的`createApp`：

```ts
export function createApp(...args) {
  return renderer.createApp(...args);
}
```

所以用户调用的`createApp(App).mount(container)`，最后还是会走`runtime-core`的组件初始化和patch流程。

### 四、custom renderer的使用方式

如果目标平台不是浏览器DOM，只需要提供相同含义的host函数。例如一个绘图库可能需要：

```ts
const renderer = createRenderer({
  createElement(type) {
    return createPlatformNode(type);
  },

  patchProp(el, key, prevVal, nextVal) {
    el[key] = nextVal;
  },

  insert(el, parent) {
    parent.addChild(el);
  },

  remove(el) {
    parent.removeChild(el);
  },

  setElementText(el, text) {
    el.text = text;
  }
});
```

挂载时不再传入DOM容器，而是传入目标平台的根节点：

```ts
renderer.createApp(App).mount(platformRoot);
```

组件仍然可以使用同样的`h`、`setup`、`ref`和组件通信能力，变化的只是节点创建和插入方式。

仓库中的示例位于：

```text
packages/vue/examples/customRenderer/main.js
```

示例使用`PIXI`创建画布节点，并把自己的创建和插入逻辑传给`createRenderer`。

### 五、renderer抽象带来的好处

把运行时拆成core和platform以后，业务逻辑和平台API之间的关系变成：

```text
组件render
    ↓
vnode
    ↓
runtime-core的patch
    ↓
hostCreateElement / hostPatchProp / hostInsert
    ↓
DOM、Canvas或其它平台
```

这样做至少带来三个好处：

1. 组件和响应式逻辑不用绑定浏览器；
2. 平台层可以独立替换；
3. runtime-core更容易测试，因为可以传入一套内存节点或测试节点操作。

### 六、和runtime-test的关系

如果测试运行时逻辑，不一定要真的创建浏览器DOM。可以提供一套简单的测试host：

```ts
const renderer = createRenderer({
  createElement(type) {
    return {
      type,
      children: [],
      props: {}
    };
  },

  patchProp(el, key, prevVal, nextVal) {
    el.props[key] = nextVal;
  },

  insert(child, parent) {
    parent.children.push(child);
  },

  remove(child) {
    // 从父节点中删除
  },

  setElementText(el, text) {
    el.text = text;
  }
});
```

这种host实现不需要浏览器环境，就可以观察组件是否正确生成了节点、更新了props以及处理了children。

### 七、当前实现的边界

当前的custom renderer已经把核心host接口抽出来，但仍然是学习版实现：

- 平台节点的属性更新规则需要由具体平台自行完善；
- 事件、样式和特殊节点需要平台层单独处理；
- 当前`Text`分支仍然使用了浏览器文本节点API；
- 完整Vue还会提供更丰富的renderer选项。

这些边界也正好说明了抽象的价值：核心流程可以保持稳定，新增平台能力时只扩展host层。
